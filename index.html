Why Sales Planning?

기획부터 실행, 성과 확인까지 한 흐름으로 프로젝트를 진행하였습니다. 데이터를 근거로 의사결정을 하고 시장·고객 관점에서 문제를 나눈 뒤, 실행 조건을 정리해 프로세스를 개선하였습니다. 개발·운영 등 여러 역할과 맞춰 가며 실행하고, 집계 조건으로 성과를 확인하는 일을 반복하였습니다.

  • 데이터 기반 의사결정 - 원천 데이터와 화면 결과를 대조해 판단 근거를 남겼습니다.
  • 시장 및 고객 관점 - 사용자·역할별로 막히는 지점을 기준으로 문제를 정의하였습니다.
  • 문제 분석 - 환경 차이, 권한, 집계 조건처럼 원인이 갈리는 지점을 나눠 보았습니다.
  • 프로세스 개선 - 끊기는 업무 흐름을 다시 잇고, 같은 조건으로 재확인하였습니다.
  • 부서 간 협업 - 개발·운영과 기준을 맞춰 실행하고, 결과를 문서화해 공유하였습니다.
  • KPI 관리 - 기간, 역할, 집계 단위를 나눠 성과를 볼 수 있게 하였습니다.
  • 실행력 - 분석에서 그치지 않고 화면·프로세스·보고까지 직접 실행하였습니다.


개발을 이해한 상태에서 데이터를 분석하고, 여러 부서와 협업해 실행 전략을 수립하는 영업기획 업무를 하고자 합니다.

Business Planning Process

실행에 들어가기 전에 시장과 문제를 보고, 데이터로 조건을 나눈 뒤 전략을 실행하고 성과를 다시 확인하였습니다.

01

시장 및 문제 분석

사용자가 어디에서 막히는지 보고, 업무가 어떤 조건을 충족해야 하는지 먼저 정리하였습니다.

→
02

데이터 분석 및 인사이트 도출

기간, 역할, 화면 흐름처럼 의사결정에 필요한 조건을 나눠 인사이트로 정리하였습니다.

→
03

실행 전략 수립

정리한 조건을 화면과 프로세스로 옮기고, 개발·운영과 맞춰 가며 실행하였습니다.

→
04

성과 분석 및 개선

실행 결과를 기준과 대조하고, 문제가 있으면 원인을 고친 뒤 같은 조건으로 성과를 다시 확인하였습니다.

02 역할

홈 대시보드, DataStore 설정, 맥락 인식 알림 규칙 엔진, 백그라운드 Worker를 구현하였으며, Settings 기능의 운영 시나리오도 작성하였습니다.

03 요구사항 정의

복약 등록 → 설정 → 권한 → Worker → 알림 발생을 하나의 업무 흐름으로 정리하였습니다. Android 13+ 알림 권한 조건을 팀에 공유해 실행 기준을 맞췄습니다.

04 실행

설정 값과 알림 규칙, Worker가 연결되도록 구현하였습니다. 기기에 복약을 등록한 뒤 알림이 실제로 나가는지 실행하였습니다.

05 성과 확인

기능을 따로 보기보다 등록부터 알림까지 한 흐름으로 운영이 이어지는지 확인하였습니다. 권한 없는 상태, Merge 이후처럼 프로세스가 끊기기 쉬운 지점도 같이 보았습니다.

06 개선

팀 코드 Merge 이후 MedDatabase_Impl 오류가 났습니다. Logcat으로 원인을 보니 KSP 설정이 빠져 있어, 설정을 추가한 뒤 같은 환경에서 운영 안정성을 다시 확인하였습니다.

04 실행

프론트엔드 구현에 참여하였으며, 백앤드와 프론트앤드를 연결하였습니다.

05 성과 확인

로컬과 호스팅에서 같은 suburb 선택 시나리오를 실행하였습니다. Score 색상 밴드는 API 응답, 코드 처리, UI 표시가 같은지 대조하였으며, 375 / 768 / 1440px과 브라우저별 주요 화면도 확인하였습니다.

06 개선

호스팅한 사이트에서 suburb 변경 시 지도의 포커스가 변경되지 않는 이슈가 발생했습니다. 반면, 로컬에서는 이러한 오류가 확인되지 않았습니다.

Deep Dive - ourSuburb

호스팅 환경에서만 발생한 지도 포커스 문제를 운영 이슈로 보고 원인을 좁힌 사례입니다.

사용자가 선택한 suburb의 위치를 비교 화면에서 확인할 수 없는 문제를, 로컬과 호스팅 차이로 분석하였습니다.

LOCAL 정상

suburb를 선택하면 지도가 해당 위치로 이동하였습니다.

HOSTING 오류 발생

같은 동작에서 지도 포커스가 이동하지 않았습니다.

Situation

호스팅 환경에서 suburb를 선택해도 지도 포커스가 해당 위치로 이동하지 않았습니다. 로컬에서는 같은 동작이 정상이었습니다.

↓
Task

비교 화면에서 선택한 위치를 사용자가 확인할 수 있도록, 환경 차이를 기준으로 원인을 찾아야 했습니다.

↓
Action

같은 suburb 선택 시나리오를 로컬과 호스팅에서 각각 실행하고, Mapbox 스타일 로딩 시점과 지도 컨테이너 크기를 확인하였습니다. 스타일이 로드되기 전에 flyTo가 실행되었고 resize 처리가 빠져 있어, isStyleLoaded를 확인한 뒤에 flyTo를 실행하고 resize를 추가하였습니다.

if (!map.isStyleLoaded()) {
  map.once('idle', () => moveCamera(lng, lat));
  return;
}
map.resize();
map.flyTo({
  center: [lng, lat],
  essential: true
});
↓
Result

호스팅에서 같은 시나리오를 다시 실행하였으며, 선택한 위치로 지도 포커스가 이동하는 것을 확인하였습니다. LeanKit에 재현 환경, 방법, 실제 결과, 기대 결과, 원인과 수정 내용을 정리해 공유하였습니다.

↓
Business Impact

비교 화면에서 선택한 위치를 바로 확인할 수 있게 되어 사용자 경험이 개선되었습니다. 배포 환경에서만 나타나던 운영 리스크를 줄였고, 환경 차이와 수정 내용을 남겨 이후 의사결정에 쓸 근거를 확보하였습니다.

Data

FIT5147 R Shiny 프로젝트입니다. 원천 데이터를 수집·전처리하고, 비교 가능한 지표로 만든 뒤 대시보드로 시각화해 의사결정에 사용하였습니다.

데이터 수집

엔화 환율과 일본인 호주 방문 데이터를 수집하였습니다. 외부 환경 지표와 방문 규모를 같은 기간 기준으로 맞춰, 변화의 방향을 같이 볼 수 있게 하였습니다.

데이터 전처리

CSV / Excel로 원천 데이터를 정리하고, 연도별 집계와 Long Format 변환을 하였습니다. 서로 다른 출처의 데이터를 비교할 수 있는 형태로 맞췄습니다.

KPI 분석

연도별 환율과 방문 규모를 핵심 비교 지표로 두고, 두 지표가 어떻게 움직이는지 분석하였습니다. 화면에서 바로 확인할 수 있도록 집계 단위를 맞춰 두었습니다.

Dashboard / 시각화

R Shiny 대시보드에서 Plotly 클릭 이벤트와 reactiveVal을 연결해, 선택한 구간 지표를 바로 확인할 수 있게 하였습니다. 보고와 검토에 쓸 수 있는 형태로 시각화하였습니다.
